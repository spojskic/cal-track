# supabase/

Postgres schema, RLS, search RPCs and config for cal-track. Everything runs on the
Supabase **free** tier (500 MB), so the schema is deliberately lean: no per-nutrient
rows (`foods.nutrients` is one `jsonb` per 100 g) and diary entries store only
`food_id + grams`.

```
supabase/
  config.toml        Supabase CLI config (invite-only auth, API exposes `public` only)
  migrations/        plain SQL, applied in file-name order
  seed/              generated by packages/core (nutrients, DRIs, exercise activities) - see below
  functions/         edge functions (not part of this change)
tools/db-tests/      database tests (PGlite = real Postgres in WASM, no Docker)
```

## Migrations

| file                        | content                                                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `…01_extensions_helpers`    | `unaccent`, `pg_trgm` (schema `extensions`), `immutable_unaccent()`, `set_updated_at()`, `food_source_quality()`                           |
| `…02_reference_tables`      | `nutrients`, `dri_values`, `exercise_activities`, `app_settings` (+ `coach_retention_days = 90`)                                           |
| `…03_foods`                 | `foods` (generated search columns, GIN indexes), `food_portions`, GTIN normalisation trigger                                               |
| `…04_user_profile_targets`  | `profiles`, `meal_groups`, `weight_goals`, `macro_targets`, `nutrient_targets`, `handle_new_user` trigger on `auth.users`                  |
| `…05_food_logging`          | recipes, saved meals, favourites, `food_usage`, `diary_entries`, `daily_totals` cache + triggers, immutability trigger, `supersede_food()` |
| `…06_activity_health`       | exercise, biometrics, `daily_energy`, notes, water, fasts, integrations                                                                    |
| `…07_coach`                 | coach threads/messages, `purge_old_coach_messages()`, `delete_all_my_coach_data()`                                                         |
| `…08_search_functions`      | `search_foods()`, `private.search_foods_ranked()`, `get_food_by_gtin()`                                                                    |
| `…09_rls_policies`          | RLS on every table                                                                                                                         |
| `…10_grants`                | least-privilege grants (anon gets nothing)                                                                                                 |
| `…90_pg_cron_supabase_only` | **Supabase-only**: daily 03:00 UTC cron job for the coach purge                                                                            |

All migrations except the last are idempotent (`if not exists`, `create or replace`,
`drop … if exists`) and are applied twice by the tests. A migration whose file name
contains `supabase_only` needs real Supabase (pg_cron, vault, …); the test harness
skips it. Put any new Supabase-only step in such a file, **after** the portable ones.

## Link a hosted project and deploy

```bash
npx supabase login
npx supabase link --project-ref <your-project-ref>     # ref = the xxxx in https://xxxx.supabase.co
npx supabase db push                                   # applies supabase/migrations/* to the remote DB
```

`db push` does not run `seed/`. Load seeds with `psql` (connection string from
Dashboard > Project Settings > Database), in this order: `nutrients` first, then
the rest:

```bash
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/seed/<file>.sql
```

Seeds should be re-runnable: `dri_values` has no unique key on purpose, so a seed
must `delete from public.dri_values;` (or truncate) before inserting; `nutrients` and
`exercise_activities` can `insert … on conflict (code) do update`.

After a large food import run `analyze public.foods;`.

Apply the auth settings from `config.toml` to the hosted project (or set them in the
dashboard): `npx supabase config push`.

## Creating users (sign-up is disabled)

`config.toml` sets `[auth] enable_signup = false`, so the owner creates every account:

- **Dashboard (works today)**: **Authentication > Users > Add user > Create new user**, enter an email and password and
  tick *Auto Confirm User*. Give the person their password; they can sign in straight away.
- **Invite by email (does not work yet)**: the invite link expects a page where the invitee sets a password, and the
  app has none. Use the method above until one is added.

Inserting into `auth.users` fires `handle_new_user`, which creates the profile and the four default meal groups
(Breakfast, Lunch, Dinner, Snacks). Never put the service-role key in the app.

## Tests

```bash
source ~/.nvm/nvm.sh && nvm use 22
pnpm --filter @cal/db-tests test        # ~10 s
pnpm --filter @cal/db-tests typecheck
```

The tests need **no Docker**: they boot [PGlite](https://pglite.dev) (a real Postgres
compiled to WASM, with the `unaccent` and `pg_trgm` contrib extensions) and apply
`supabase/migrations/*.sql` on top of small stand-ins for what Supabase provides
(roles `anon`/`authenticated`/`service_role`, `auth.users`, `auth.uid()`, schema
`extensions`, Supabase's default privileges). Users are impersonated like PostgREST
does: `set role authenticated` + `set_config('request.jwt.claim.sub', …)`.

## Design notes

**Nutrients.** Codes are `UPPER_SNAKE` (`ENERGY_KCAL`, `PROTEIN_G`, `CARBS_G`,
`FAT_G`, `FIBER_G`, …). `foods.nutrients = {"CODE": amount_per_100g}`; a missing key
means _unknown_, never zero. A check constraint enforces "object of numbers".

**History is immutable, not copied.** A trigger rejects changes to `nutrients`,
`carb_basis` or `density_g_per_ml` of a food referenced by any `diary_entries` row or
recipe ingredient (SQLSTATE `23001`). To change such a food call
`select public.supersede_food(<id>)`: it archives the old row (global rows get
`source_id = '<id>#v<n>'`, freeing the unique slot), inserts a copy with
`version + 1` / `supersedes = old`, copies the portions, and returns the new id,
which you can then edit freely. FKs from user tables to `foods` are deferred, so
deleting a user cascades cleanly while deleting a single logged food is rejected at
commit (archive it instead).

**Search.** `public.search_foods(q, max_results, kinds)` is `SECURITY INVOKER`.
It delegates to `private.search_foods_ranked()` (`SECURITY DEFINER`, schema `private`
is not exposed by the API) and then re-checks each returned row under RLS. The split
exists because under RLS Postgres will not use an index for non-leakproof operators
(`@@`, `<%`) and would seq-scan `foods` on every keystroke; a test guards this.
Match = unaccented prefix full-text **or** trigram word-similarity (threshold 0.45,
queries ≥ 3 chars). Rank is an additive score (personal usage/own foods > source
quality > text similarity > completeness/popularity). `foods.gtin14` is **not**
unique (two sources may share a barcode); `get_food_by_gtin()` pads any GTIN to 14
digits and returns the best single row (own > source quality > completeness).
Both GIN indexes use `fastupdate = off` to avoid pending-list scans after bulk loads.

**`daily_totals`** is a cache maintained by `SECURITY DEFINER` triggers on
`diary_entries`; clients have `SELECT` only. `food_usage` is maintained by the same
trigger (insert only; it never decrements).

**Coach retention.** `purge_old_coach_messages()` deletes messages older than
`app_settings.coach_retention_days` (default 90) for users with
`profiles.coach_auto_delete = true`, then threads that are empty and stale. It is
scheduled by the Supabase-only migration. Verify with
`select * from cron.job;` and `select * from cron.job_run_details order by start_time desc limit 5;`.
Clients call `rpc('delete_all_my_coach_data')` to wipe their own coach data. No API keys
are ever stored server-side.

**Importer insert shape** (global foods; never set `id`, `search`, `search_text`,
`created_at`, `updated_at`, `version`, `supersedes`, `archived`):

```sql
insert into public.foods
  (source, source_id, kind, owner_id, name, brand, gtin14, category,
   nutrients, completeness, carb_basis, density_g_per_ml, popularity)
values
  ('fdc_foundation', '171477', 'generic', null,
   'Chicken, broilers or fryers, breast, raw', null, null, 'Poultry Products',
   '{"ENERGY_KCAL": 120, "PROTEIN_G": 22.5, "FAT_G": 2.6}'::jsonb,
   0.85, 'includes_fiber', null, 0)
on conflict (source, source_id) where source_id is not null and owner_id is null
do update set name = excluded.name, brand = excluded.brand, gtin14 = excluded.gtin14,
              category = excluded.category, completeness = excluded.completeness;
-- Changing nutrients on re-import: only for unreferenced foods, otherwise
-- select public.supersede_food(id) first and update the new row.
```

`gtin14` may be any 8–14 digit code (separators ignored); a trigger left-pads it to
14 digits and nulls unusable values.

## Real Supabase vs the PGlite tests

Not covered by the tests (verify once on the hosted project):

- **pg_cron**: the schedule is only in the skipped `…90_pg_cron_supabase_only` migration.
- **Extension schema**: migration 01 does `create extension … with schema extensions`
  and `immutable_unaccent()` pins the dictionary `extensions.unaccent`. If `unaccent`
  was already installed elsewhere (e.g. `public`), drop and recreate it first.
- **Roles/grants**: the harness imitates Supabase's default privileges; the real
  `postgres` role is not a superuser. Check with
  `select grantee, privilege_type from information_schema.role_table_grants where table_name = 'diary_entries';`
  (expect only `authenticated` CRUD + `service_role`).
- **Postgres version**: PGlite is PG 18, hosted default is 17 (composite FK
  `on delete set null (col)` needs ≥ 15). Planner/stat details can differ slightly.
- **Table owner bypasses RLS**: `SECURITY DEFINER` functions rely on being owned by
  the migration role (`postgres`); do not `force row level security`.
- **Concurrency/PostgREST**: tests use one session; PostgREST wraps each request in
  a transaction, so deferred FK errors surface at request commit.
